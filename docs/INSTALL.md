# FurriHearts — Installation Guide

How to stand up a complete FurriHearts environment (database + app) from scratch.
Written against a full introspection of the production database on **2026-07-04**
(Postgres 17.6, Supabase). Follow the sections in order.

---

## 1. Overview & architecture

| Layer | Technology | Notes |
|---|---|---|
| Frontend/backend | Next.js 16 (App Router) + React 19 | Single codebase; server actions for privileged operations |
| Database | Supabase Postgres | 11 tables in `public`, RLS everywhere |
| Auth | Supabase Auth | Email/password + Google OAuth; profiles auto-created by a DB trigger |
| Storage | Supabase Storage | `pet-photos` (public), `boost-receipts` (private, signed URLs) |
| Scheduled jobs | pg_cron (inside Postgres) | Nightly message archival |
| Hosting | Vercel (or any Node host) | Auto-deploys from `main`; no `vercel.json` needed |
| Email | Supabase Auth built-in | Password reset / confirmation emails; no third-party mail service |
| Payments | None | Boost feature uses manual receipt verification by auditors |

There are **no other external services** — no Stripe, no SMS, no analytics, no
error tracking. Everything runs on Supabase + the Next.js host.

### Key repository paths

| Path | Purpose |
|---|---|
| `supabase/setup/init.sql` | **Full database initialization for a new environment (start here)** |
| `supabase/setup/verify.sql` | Read-only self-check to run after `init.sql` |
| `supabase/migrations/` | Incremental history of the *existing* production DB — do **not** replay these on a new project; `init.sql` already contains their net result plus dashboard-created objects the migrations never captured |
| `supabase/maintenance/` | One-off UAT cleanup/seeding scripts; never part of installation |
| `.env.local` | Local secrets (gitignored) — see section 6 |

## 2. Prerequisites

- Node.js 20+ and npm
- A Supabase account (free tier is sufficient)
- A Vercel account (or any host that runs `next build` / `next start`)
- Optional: a Google Cloud project if you want Google sign-in

---

## 3. Create the Supabase project

1. [supabase.com](https://supabase.com) → **New project**. Pick a region close to
   your users (production uses Singapore, `ap-southeast-1`) and set a strong
   database password — store it in a password manager; you'll need it for any
   direct `psql`/`pg_dump` access later.
2. From **Project Settings → API**, record three values:
   - **Project URL** → `NEXT_PUBLIC_SUPABASE_URL`
   - **anon public key** → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - **service_role key** → `SUPABASE_SERVICE_ROLE_KEY` (server-only secret;
     bypasses RLS — never expose it to the browser or commit it)

---

## 4. Initialize the database

1. Open **SQL Editor** in the Supabase dashboard.
2. Paste the entire contents of [`supabase/setup/init.sql`](../supabase/setup/init.sql)
   and run it. It is idempotent (safe to re-run) and creates:
   - all 11 tables with constraints, defaults and indexes
   - all 5 functions and 4 triggers — including `on_auth_user_created` on
     `auth.users`, which **auto-creates a `profiles` row on every signup**
   - all 32 RLS policies (29 public + 3 storage), reproduced faithfully from
     production, with legacy duplicates marked in comments
   - both storage buckets and their policies
   - the 16-state `state_rollouts` seed data
   - the nightly `archive-ended-messages` pg_cron job (03:17 UTC)
3. If the `create extension pg_cron` line fails with a permissions error,
   enable pg_cron under **Database → Extensions** first, then re-run the file.
4. Run [`supabase/setup/verify.sql`](../supabase/setup/verify.sql) in the SQL
   Editor. **Every row must show `ok = true`** (15 checks). A failing row names
   the section of `init.sql` to re-run.

> **Why not the migrations folder?** The base tables (`profiles`, `pets`,
> `applications`), both storage buckets, the `handle_new_user` trigger and the
> `sync_pet_status_on_app_update` trigger were created by hand in the dashboard
> and never captured in `supabase/migrations/`. `init.sql` was generated from a
> live introspection and is the only complete definition. Keep using
> `supabase/migrations/` for *future incremental changes* on an existing
> environment.

## 5. Storage buckets

`init.sql` already creates both buckets via SQL. Confirm under **Storage**:

| Bucket | Visibility | Used for | Policies |
|---|---|---|---|
| `pet-photos` | **Public** | Pet listing photos (uploads from the listing flow) | public read + public insert |
| `boost-receipts` | **Private** | Payment receipt uploads for listing boosts | authenticated insert only; **no read policy** — receipts are only viewable through 60-second signed URLs generated by the auditor panel (service role) |

If you prefer creating buckets in the dashboard instead (Storage → New bucket),
match the visibility above; the policies are applied by `init.sql` either way.

---

## 6. Auth configuration (dashboard)

These settings live only in the Supabase dashboard — no code or SQL captures them.

1. **Authentication → URL Configuration**
   - **Site URL**: your production domain, e.g. `https://your-domain.com`
   - **Redirect URLs**: add
     - `https://your-domain.com/auth/callback` (OAuth + email confirmation)
     - `https://your-domain.com/reset-password` (password reset)
     - plus `http://localhost:3000/...` equivalents for local development
2. **Authentication → Email Templates**: the defaults work. The app relies on
   the *Reset Password* and *Confirm signup* templates.
3. **Authentication → Providers → Google** *(optional — skip to disable Google sign-in)*
   - In Google Cloud Console → APIs & Services → Credentials, create an
     **OAuth client ID** (Web application). Authorized redirect URI:
     `https://<project-ref>.supabase.co/auth/v1/callback` (shown in the
     Supabase provider panel).
   - Paste the Client ID and Client Secret into the Supabase Google provider
     settings and enable it.

Signup flow note: when a user signs up, the **database trigger**
`on_auth_user_created` inserts the `profiles` row (taking `first_name`/`last_name`
from the signup metadata). The app code in `app/actions/auth.ts` also attempts
an insert as a fallback; it harmlessly no-ops on conflict.

## 7. Deploy the app

1. Clone the repository and install dependencies:
   ```bash
   git clone <repo-url> && cd furrihearts
   npm install
   ```
2. Configure environment variables (`.env.local` locally; Project → Settings →
   Environment Variables on Vercel):

   | Variable | Exposure | Purpose |
   |---|---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | public | Supabase project URL |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | public | Browser client key (RLS-restricted) |
   | `SUPABASE_SERVICE_ROLE_KEY` | **server-only secret** | Admin/auditor server actions, signed receipt URLs |

3. Deploy:
   - **Vercel**: import the repo; framework auto-detected; pushes to `main`
     auto-deploy. No extra config file is needed.
   - **Self-hosted Node**: `npm run build && npm start` (port 3000).
4. Local development: `npm run dev` with the same three variables in `.env.local`.

> Deployments never touch the database. Any future SQL change must be applied
> manually in the SQL Editor (add it to `supabase/migrations/` for history).

---

## 8. Post-install setup

1. **First admin**: sign up normally through the site, then in Supabase
   **Table Editor → profiles** set that user's `is_admin = true`. There is
   deliberately no in-app way to grant admin.
2. **Auditors**: as the admin, open `/admin/users` and toggle auditor status.
   Auditors review listings and boost receipts at `/auditor`.
3. **Launched states**: `/admin/locations` toggles which Malaysian states are
   open. The seed marks Kuala Lumpur, Selangor, Penang, Johor and Melaka as
   launched (production snapshot); adjust as needed. If the table were ever
   empty the app falls back to showing all 16 states.

**Known drift & cleanup candidates** (reproduced as-is by `init.sql` for parity):

- Legacy duplicate RLS policies on `pets`, `profiles` and `applications`.
- Two **permissive legacy INSERT policies** — `pets` "Enable insert access for
  all users" and `applications` "Allow public inserts for applications", both
  `WITH CHECK (true)`. Because policies are OR-ed, these override the stricter
  owner-scoped insert policies. Works, but worth tightening in a future pass.
- `types/supabase.ts` is stale (contains only 3 of 11 tables). Regenerate with
  `npx supabase gen types typescript --project-id <ref> --schema public` when convenient.

## 10. Migrating data from an existing project (optional)

To move *data* (not just schema) into the new environment:

1. **Database**: run `init.sql` first (schema), then copy data with pg_dump
   against the old project's **Session pooler** connection string:
   ```bash
   pg_dump "$OLD_DB_URL" --data-only --schema=public \
     --exclude-table=public.state_rollouts > data.sql   # seed already present
   psql "$NEW_DB_URL" -f data.sql
   ```
2. **Auth users**: use Supabase's built-in migration tooling or the Admin API
   (`GET /auth/v1/admin/users` on the old project → `POST` on the new one);
   password hashes migrate only via Supabase support / CLI `auth` dump.
   The `on_auth_user_created` trigger will fire on imported users — either
   import profiles first and rely on the conflict no-op, or temporarily disable
   the trigger during import.
3. **Storage objects**: download and re-upload per bucket (Supabase CLI:
   `supabase storage cp --recursive`, or a script using the two service keys).
   `pets.image_url`/`gallery` store absolute URLs pointing at the old project —
   rewrite the host in the copied data, e.g.
   `update pets set image_url = replace(image_url, 'https://<old-ref>.supabase.co', 'https://<new-ref>.supabase.co');`
   (and the same for `gallery`, `messages`, `listing_boosts.receipt_url`).

## 11. Maintenance notes

- **Message archival**: conversations whose application has been terminal
  (rejected/cancelled/closed) for 90+ days move to `messages_archive` nightly.
  Monitor with `select * from cron.job_run_details order by start_time desc limit 20;`
  Manual run: `select public.archive_ended_message_threads(90);`
- **`supabase/maintenance/`**: one-off UAT scripts (orphan cleanup, test pet
  seeding/removal). Read each header before use; they reference specific test
  accounts and are not part of any installation.
- **Moderation columns** (`pets.review_status`, `pets.is_featured`) can only be
  changed through service-role server actions — a DB trigger silently reverts
  changes from regular users.
- **Application lifecycle**: approving an application auto-adopts the pet and
  auto-rejects competing pending applications (DB trigger
  `sync_pet_status_on_app_update`); messaging is blocked server-side once an
  application is rejected/cancelled/closed.

## 12. Verification checklist (smoke test)

After completing sections 3–8, verify end-to-end on the deployed site:

1. **Signup** with a fresh email → confirm a `profiles` row appeared with the
   first/last name populated.
2. **Login / logout**; **password reset** (email link must land on
   `/reset-password` and let you set a new password).
3. **Google sign-in** (if enabled) → lands on `/auth/callback` → profile created.
4. **Create a listing** as a rescuer: upload photos (crop one, set a non-first
   photo as main), publish → photos appear in the `pet-photos` bucket; listing
   shows on `/browse` with the chosen main photo.
5. **Apply** for a pet from a second account; the rescuer sees it in
   `/manage-applications`.
6. **Messaging**: adopter messages the rescuer; unread badge appears on the
   rescuer's navbar within 60 seconds; clicking the notification opens the
   conversation; count clears after reading.
7. **Approve** the application → pet flips to adopted, other pending
   applications auto-reject, messaging on closed threads is blocked.
8. **Admin**: `/admin` reachable for the admin user; toggle a state in
   `/admin/locations` and confirm the listing form's location dropdown updates.
9. **Cron**: `select * from cron.job;` shows `archive-ended-messages` active.
